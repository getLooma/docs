## Why

Looma has no public user documentation. The owner wants every user-facing document in one open
source repository so that anyone, including people outside the team, can fix and extend it, and
so that each user-facing change to the product lands with a matching docs change. The docs also
have to be easy for AI assistants to read and cite, and strong in search engines, because that is
where most people will meet them first.

This repository holds only a one-line README today. This change sets it up: the site, the tooling,
the rules for contributors, the checks, and the hosting at docs.getlooma.io. It writes no
documentation pages beyond a home page; the first pages are a later change.

## What Changes

- **Site:** an Astro Starlight site at the repository root. Pages are Markdown under
  `src/content/docs/`, configured in `astro.config.mjs` and `src/content.config.ts`. Search is
  Starlight's built-in Pagefind.
- **Information architecture:** eight top-level sections with fixed URL prefixes: Getting started
  (`/getting-started/`), Inbox and conversations (`/inbox/`), Issues (`/issues/`), AI replies and
  analysis (`/ai/`), Integrations (`/integrations/`, Shopify first), Team and roles (`/team/`),
  Privacy and data requests (`/privacy/`) and FAQ (`/faq/`). A section appears in the sidebar
  when its first page lands.
- **Licensing:** docs text under CC BY 4.0 (`LICENSE-docs`), site code and config under MIT
  (`LICENSE`). `README.md` and `CONTRIBUTING.md` say which applies to which paths.
- **Contributors:** `CONTRIBUTING.md` (how to propose an edit, the review rules, the sign-off
  rule), `STYLE_GUIDE.md` for user-facing writing, `.github/PULL_REQUEST_TEMPLATE.md`, issue forms
  under `.github/ISSUE_TEMPLATE/`, `.github/CODEOWNERS`, `SECURITY.md` and `CODE_OF_CONDUCT.md`.
- **Who merges:** anyone may open issues, join discussions and open pull requests from a fork.
  Only the team `@getLooma/docs-maintainers` has write access and merges. `main` is protected by
  the ruleset `main`, kept as code in `.github/rulesets/main.json` and applied with
  `just ruleset-apply`. Its rules are phased:
  - phase 1, applied now: pull requests only, no force pushes or deletion, squash merge only;
  - phase 2, once CI exists: required status checks;
  - phase 3, once a second team member joins: required code-owner approval.

  Repository settings (fork-PR workflow approval, a read-only default `GITHUB_TOKEN`, SHA-pinned
  actions) are kept as code in `scripts/repo-settings`.

- **AI readability:** `/llms.txt`, `/llms-full.txt` and one bundle per section, generated by the
  `starlight-llms-txt` plugin. A Markdown copy of every page at `<page>.md`. "Copy page as
  Markdown" and "Open in ChatGPT / Claude" buttons from the `starlight-page-actions` plugin.
  Content negotiation: a request with `Accept: text/markdown` gets the Markdown copy. A
  `robots.txt` that allows AI crawlers and links the sitemap and `/llms.txt`.
- **SEO:** static prerendered pages with a trailing-slash URL policy, canonical URLs, a required
  unique title and description on every page, Open Graph and Twitter tags with a generated image
  per page, `sitemap-index.xml`, JSON-LD (`Organization`, `BreadcrumbList`, `TechArticle`,
  `FAQPage` on the FAQ), `lang="en"` with i18n ready, and permanent redirects for moved pages.
- **Checks (`just check`):** Prettier, the frontmatter schema, a built-site check (one `h1`,
  ordered headings, alt text, unique titles and descriptions, canonical links, JSON-LD, `.md`
  copies, `llms.txt` and the sitemap non-empty, a client JavaScript budget), a redirect check
  that fails when a published page disappears without a redirect, internal link validation
  (`starlight-links-validator`), a public-content scan (`gitleaks` plus generic patterns),
  Looma-terminology prose lint (Vale), `actionlint`, and the check scripts' own tests (vitest).
- **Tooling:** the Nix dev shell grows from the minimal one created for OpenSpec to the full
  set (`flake.nix`); a `justfile`; Prettier with `prettier-plugin-astro`; a Husky + lint-staged
  pre-commit hook; `CLAUDE.md`, `.claude/settings.json` and the OpenSpec skills.
- **CI (`.github/workflows/`):** `ci.yml` runs `just check` on every pull request, fork PRs
  included, with no secrets. `deploy.yml` builds the image and deploys from `main` only.
  `links.yml` checks external links weekly. `pr-review.yml` is an advisory review on same-repo
  pull requests only.
- **Hosting:** a small image (`ghcr.io/getlooma/docs`, Caddy serving the built site) run by a
  Coolify Docker Image application at docs.getlooma.io. Caddy gives real `301` redirects and
  `Accept: text/markdown` negotiation, and an own image leaves room for a small runtime later.
- **Drafted pull requests:** a docs pull request drafted automatically from a released product
  change arrives from the Looma docs bot on a `drafts/` branch, labelled `drafted`. It is
  reviewed and merged by a maintainer like any other pull request.

Scaffolding already on the branch:

- a minimal `flake.nix` (Node, pnpm, Prettier, just), `flake.lock`, `.envrc`, `.gitignore`,
  `.prettierrc`, `scripts/openspec` and `openspec/config.yaml`, created so `openspec` could run
  for this change;
- `.github/rulesets/main.json`, matching the phase 1 ruleset the owner applied, and a `justfile`
  with `ruleset-apply` and `ruleset-check`.

## Non-goals

- Writing documentation pages. Only a home page ships here.
- Translations. The site is English only; i18n is configured so a locale can be added later
  without changing any URL.
- The automation in the private code repositories that drafts docs pull requests. It is a change
  in those repositories; this repository only defines how it receives those pull requests.
- A docs MCP server is a separate follow-up change.
- Preview deploys for pull requests (deferred; see design.md).
- A Lighthouse CI budget (follow-up; a cheaper JavaScript budget is checked instead).
- API or developer reference docs. Looma has no public API to document yet.
- Analytics or cookies on the docs site.

## Capabilities

### New Capabilities

- `docs-site`: the Starlight site, its information architecture, URL scheme, licensing split and
  local tooling.
- `docs-discoverability`: how the site serves AI assistants and search engines (`llms.txt`,
  Markdown copies, content negotiation, `robots.txt`, metadata, sitemap, structured data,
  redirects).
- `docs-contributing`: how people propose edits, how pull requests are reviewed and merged, the
  templates and the writing style, and how drafted pull requests are received.
- `docs-delivery`: the CI checks, the public-content safety rules, fork safety and the deploy to
  docs.getlooma.io.

### Modified Capabilities

None. This is the repository's first change.

## Impact

- New repository content only. No product code, data or schema is touched.
- New dependencies, all pinned in `package.json` and listed in design.md: `astro`,
  `@astrojs/starlight`, `starlight-llms-txt`, `starlight-page-actions`,
  `starlight-links-validator`, `astro-og-canvas`, `prettier`, `prettier-plugin-astro`, `husky`,
  `lint-staged`, `vitest`, `node-html-parser`. From nixpkgs: `vale`, `lychee`, `gitleaks`,
  `actionlint`.
- Owner actions: the `@getLooma/docs-maintainers` team, the later ruleset phases, the DNS record for docs.getlooma.io, the Coolify application and its deploy-only
  token, the repository settings (branch protection, fork-PR approval, Actions permissions), and
  Search Console verification. See tasks.md section 9.
